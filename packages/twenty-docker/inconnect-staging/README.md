## Procedencia y diseño del build

1. Empaquetar únicamente fuente versionada del SHA indicado, desde un árbol materializado en un directorio de build separado. Registrar SHA, hashes de contexto y Dockerfile, plataforma y procedencia. Revisar el contexto completo antes de entregarlo a BuildKit y fallar si contiene dotenv reales (`.env`, `.env.test`, `.env.local`, etc.), secretos, credenciales Git/registro, certificados privados, `.git`, cachés, `node_modules`, almacenamiento o artefactos locales. Conservar las plantillas versionadas sin secretos sólo cuando se necesiten. La [.dockerignore](../../../.dockerignore) oficial excluye algunos dotenv concretos. La selección del contexto debe cubrir también los demás. Excluir `packages/twenty-front/build` y outputs locales para que el Dockerfile compile el frontend de ese mismo SHA.
2. Usar el [Dockerfile del checkout](../twenty/Dockerfile), target `twenty` con BuildKit, y conservar el `WORKDIR` `/app/packages/twenty-server` y UID `1000`. El target copia el frontend en `dist/front` y hereda el backend compilado. La base alcanzable en ese target es `node:24.18.0-alpine3.23@sha256:595398b0081eacda8e1c4c5b97b76cd1020e4d58a8ebcb4843b9bca1e79e7436`. Registrar también el digest resuelto para la arquitectura de la VM. `twenty-app-dev` usa s6, base y runtime diferentes, e integra init, cron, PostgreSQL, Redis y worker. Queda excluido del diseño de staging.
3. Usar Yarn `4.13.0`, la release versionada y el lockfile del SHA (`sha256:472cf6982919d1c7afe1fb54acebc9fe1d4fa14add05ddb806b01006e5a3e568`). La futura fase de build debe validar el contexto completo con `yarn install --immutable` y comprobar el hash antes y después. El Dockerfile usa `yarn workspaces focus`, incluida la reducción a dependencias de producción. La implementación versionada usa `persistProject: false` para `focus`. Eso por sí solo no prueba que las resoluciones en memoria correspondan al lockfile. Verificar el Yarn efectivo y reconciliar las resoluciones y artefactos de cada fase de `focus` con el lockfile. Fallar si hay versiones o integridades fuera de la clausura revisada. Mantener el Dockerfile upstream intacto. Si su ruta no permite acreditar esa condición, detener el build para revisión separada.
4. La base fijada y el lockfile dan entradas identificables. Para repetir el resultado, fijar también las entradas efectivas de los repositorios de APK y de paquetes. El Dockerfile tiene mínimos de versión en `apk add`, por lo que las fuentes móviles aún pueden cambiar el resultado. Usar mirrors o snapshots aprobados, sin credenciales por `ARG`, `ENV`, URL, `COPY` ni comandos que las dejen en layers o logs. Si hicieran falta credenciales privadas, revisar primero un mecanismo efímero del builder fuera del contexto. Medir capacidad de build por separado. El Dockerfile permite un heap de hasta 8 GiB para compilar el frontend, además de otros consumos.
5. Proponer `APP_VERSION=2.32.0`, que coincide con `TWENTY_CURRENT_VERSION` de este SHA, y guardar el SHA completo por separado en la etiqueta de imagen y `org.opencontainers.image.revision`. El `version` del paquete raíz pertenece al monorepo y el SHA no es una versión semver de la aplicación. Registrar manifiesto, plataforma, hashes, resultado de build, artefacto frontend y digest OCI antes de aceptar `STAGING_INCONNECT_IMAGE`. Usar la misma identidad de imagen para cualquier worker futuro sujeto a su propio gate. Las tres variables de imagen requieren referencias aprobadas y presentes localmente, con formato `repositorio:versión@sha256:<digest>`. Los valores, la disponibilidad local y la coincidencia del digest con la plataforma quedan pendientes. No hay imagen pública de Twenty ni resolución automática de tags.

Es un diseño de build con trazabilidad, sin resultado de compilación o reproducibilidad acreditados. No se resolvieron digests de PostgreSQL ni Redis. El Compose consume imágenes y carece de una sección `build`.

## Secretos y configuración futura

- Tras autorización específica, generar dentro del laboratorio valores aleatorios nuevos e independientes para el bootstrap PostgreSQL, el login de aplicación PostgreSQL, Redis, `APP_SECRET` y `ENCRYPTION_KEY`. Usar 32 bytes de CSPRNG por valor, por ejemplo `openssl rand -hex 32` mediante un flujo de custodia que no imprima ni registre el secreto. Guardarlos en el gestor de secretos del laboratorio o en un archivo protegido fuera del repositorio y del contexto, con acceso restringido y permisos `0600`. Guardar respaldo protegido de las claves junto con el plan de recuperación. Nunca pegar URLs o secretos en tickets, logs, comandos con argumentos visibles o resultados de `compose config`. Compose y los operadores con acceso al daemon forman parte de la frontera de confianza.
- `STAGING_PG_BOOTSTRAP_PASSWORD` alimenta `POSTGRES_PASSWORD_FILE` mediante un secreto Compose. La imagen PostgreSQL inicializa el volumen vacío y `inconnect_staging` con `inconnect_staging_bootstrap`, un rol privilegiado de inicialización. Ese secreto no se inyecta en `twenty-staging`. Queda por aprobar la identidad que ejecutará cada DDL y el rol de runtime con sus permisos mínimos compatibles con Twenty, incluidos los efectos del aprovisionamiento de workspaces. `PG_DATABASE_URL` futura apuntará a `postgresql://<rol-runtime>:<secreto-codificado>@pg-staging:5432/inconnect_staging` y se entregará al entorno de proceso. Omitir `PG_DATABASE_REPLICA_URL`. Core y Raw usan `.env` sólo como fallback, con `override: false`. [Entrypoint de PostgreSQL](https://github.com/docker-library/postgres/blob/master/docker-entrypoint.sh).
- `STAGING_REDIS_ACL` alimenta `/run/secrets/staging_redis_acl` con el contenido ACL, incluidas las separaciones de línea. La propuesta usa dos líneas `user default reset off` y `user inconnect_staging_runtime reset on #<sha256-hex-del-secreto-redis> ~* &* +@all` como formato, con hash real calculado sobre los bytes de la contraseña sin salto final. El usuario dedicado tendría permisos amplios dentro del Redis exclusivo para compatibilidad inicial con caché, Pub/Sub y BullMQ. Revisar la ACL efectiva, permisos de lectura del secreto y mínimo conjunto compatible antes de aprobar el servicio. `REDIS_URL` futura será `redis://inconnect_staging_runtime:<secreto-codificado>@redis-staging:6379/0`. Omitir `REDIS_QUEUE_URL` para que el cliente de colas use `REDIS_URL`. Es un solo Redis dedicado, no una separación de dominios de fallo. La persistencia de la cola no otorga autoridad para ejecutar sus trabajos. [ACL de Redis](https://redis.io/docs/latest/operate/oss_and_stack/management/security/acl/) · [Secretos en Compose](https://github.com/compose-spec/compose-spec/blob/main/09-secrets.md).
- Entregar `APP_SECRET` y `ENCRYPTION_KEY` como entradas independientes del proceso futuro. Omitir `FALLBACK_ENCRYPTION_KEY` en una instalación nueva. `NODE_PORT=3000` fija el listener y `SERVER_URL=http://127.0.0.1:3000` presupone el mismo puerto local en el túnel. El frontend compilado usa el origen del navegador después de que `generateFrontConfig()` limpia el valor embebido en `dist/front/index.html`. `STORAGE_TYPE=local` y `STORAGE_LOCAL_PATH=.local-storage` usan el volumen dedicado. Verificar escritura con UID `1000`, origen, sesión, enlaces y redirects sobre el túnel antes de aprobar HTTP.
- `EMAIL_DRIVER=LOGGER` evita el envío SMTP y puede registrar el contenido de correos y enlaces. `EMAILING_DOMAIN_DRIVER=LOG` simula localmente el servicio de dominios de correo. Limitar esta futura etapa a datos sintéticos con acceso restringido a logs. La plantilla deshabilita explícitamente OAuth Google/Microsoft, sus integraciones de mail/calendario, billing, telemetría, FDW y el cron de Marketplace. Excluir credenciales y conexiones de Twilio, S3, SES, SMTP, ClickHouse, proveedores de IA, Sentry y exportadores externos. Revisar configuración efectiva, defaults y overrides de base de datos antes de exponer HTTP. La ausencia de credenciales y los flags no sustituyen el perímetro ni habilitan configuración de Roles, Teams, Record Access o F13.

## Entrada y matriz de inicialización

El [entrypoint oficial](../twenty/entrypoint.sh) consulta por `core` con `psql` cuando las migraciones están habilitadas. Si falta el esquema, llama a `database:init:prod`. Luego intenta `cache:flush`, `upgrade` y otro `cache:flush`. Aparte, intenta `cron:register:all` y al final hace `exec` del CMD. Puede continuar ante errores de caché, upgrade o cron. El Compose oficial cambia el CMD del worker a `yarn worker:prod`, conservando el entrypoint heredado. En S0, `twenty-staging` reemplaza el entrypoint por `/bin/sh -c` con un mensaje fijo y `exit 1`, y vacía el CMD. La barrera es el reemplazo de entrada, independiente de `DISABLE_DB_MIGRATIONS` y `DISABLE_CRON_JOBS_REGISTRATION`. Ambos valores `true` se mantienen por defensa adicional y sólo se comprobaron como guardas del script oficial.

El candidato para revisión posterior es el CMD de la imagen `node dist/main`, invocado directamente desde el `WORKDIR` oficial con el entrypoint de imagen sustituido. No está habilitado en S0. Eso excluiría la cadena de shell, pero `main.ts` inicializa Nest, AppModule, datasources, Redis, sesiones y configuración del frontend. El DataSource Core normal fija `synchronize: false` y `migrationsRun: false`, pero no fija `installExtensions: false` como el DataSource temporal de INSTALL-F1. Se deben auditar inicializadores, SQL, colas, configuración y escrituras del binario real antes de aprobar la entrada directa. El endpoint `/healthz` o la existencia de `core` por sí solos no prueban instalación completa ni permisos correctos.

## Compatibilidad y actualizaciones upstream

Se reutilizan el Dockerfile y sus rutas oficiales para código, frontend y almacenamiento local, así como la interfaz de variables del checkout. El [Compose oficial](../docker-compose.yml) y su [instalador](../scripts/install.sh) conservan su propia lógica. Staging se despliega con un modelo independiente, no como overlay del oficial. La instalación futura depende del mecanismo oficial de bootstrap y upgrades del fork y de su revisión por SHA. Evitar mezclar archivos Compose, reutilizar volúmenes del instalador o actualizar cambiando un tag público.

En cada integración upstream, volver a revisar el Dockerfile, la ruta de ejecución y el UID, la selección de Yarn y APK, la compatibilidad PostgreSQL/Redis y la configuración de frontend/sesiones. Repetir la regresión del bootstrap sobre el TypeORM adoptado y comprobar que las migraciones congeladas sigan siendo SQL directo. Comparar registros, cursores, dependencias, comandos diferidos y modos de tracking antes de cualquier upgrade. Auditar inicializadores, jobs, controles INCONNECT y regresiones de Record Access, Owner Integrity, F13 y Messaging. Un rollback de imagen requiere verificar compatibilidad con el esquema ya escrito. Conservar datos y tracking y revisar restauración bajo su autorización específica.
